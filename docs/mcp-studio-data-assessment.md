# MCP 专题：控制台数据准备阶段的综合数据评估（LIVO Studio · 数据源页）

日期：2026-09-29 · 分支 `fusion/56c6896-ins-attitude` · 前置文档：`docs/mcp-colour-only-and-time-offset-audit.md`（§12 truck05 数据裁定）、`docs/mcp-studio-v2-workflow.md`

## 1. 结论

1. LIVO Studio「数据源」页新增 **数据评估** 卡片：一次流式读取录制数据，按 7 组 42 项指标给出 正常 / 关注 / 异常 三级判定，每项标明补救类别；**凡是标定自动微调无法补偿的问题，单独列入页首的橙/红色「警示」区**。指标与阈值全部来自本项目在 truck29 / truck05 上真实踩过的坑（§3 逐项给出依据）。
2. 两车实测：**truck29 → 全部 42 项正常，结论「数据质量达到 truck29 参照水平」，7.0 s**；**truck05 → 10 项关注、0 项异常，其中 5 项「标定无法补救」（全部来自 RTK/INS 参考系统），36 s**。这与 §12 的裁定一致：truck05 精度上限由数据决定，不是标定或算法问题。
3. 地面阶段「行驶段地面修正后雷达残余俯仰」：**不改代码**。理由见 §6——现有 driven 第 2 遍已经在行驶段用地面约束求解后雷达俯仰（v066：后雷达地面厚度 4.00 → 3.12 cm），再加一个阶段只会增加标定时间而不会提高 truck29 精度；用户前提是"不影响效率才做"。
4. 评估通过 Studio 的作业系统运行（进度抽屉、日志、结果归档），报告以数据身份（路径 + 起止时间戳）为键缓存在 `results/.studio/assess/`，换数据或数据变化即自动失效；工作台数据源卡片显示评估徽标。

## 2. 使用方式

| 入口 | 说明 |
|---|---|
| 控制台 | 数据源页 → 「数据评估」卡片 → **开始评估**（已有报告时为「重新评估」）。评估作为作业运行，进度在右侧抽屉；结束后卡片自动刷新。任一作业运行时按钮禁用（避免与建图/标定争抢 I/O）。 |
| 工作台 | 数据源卡片徽标：`评估 · 正常 / 关注 / 异常 · N 项不可标定补救`；未评估显示「未评估」。 |
| API | `GET /api/datasets/assessment?path=` → `{path, file, result|null}`；`POST /api/datasets/assess {path, mine, truck}` → 作业文档（同一时刻只允许一个评估作业）；`/api/overview.assessment` 为摘要。 |
| 命令行 | `/usr/bin/python3 tools/livo/assess.py <数据目录> [--calibration <calibration.json>] [--json out.json] [--window 起点 s 时长 s] [--sample-every 6] [--camera-samples 8] [--no-camera] [--quiet]`，终端打印同一张表。 |

传入 `mine/truck` 时使用该车当前激活标定（`calibration.vehicle_status(...).calibration_file`）做静止段雷达间外参一致性检查；没有标定文件时该两项显示「未提供标定文件」，其余不受影响。

## 3. 指标体系、阈值与依据

补救类别（决定是否进入「警示」区）：

| 类别 | 含义 | 页面标签 |
|---|---|---|
| `auto` | 建图起步自检 / 合帧容差 / 时间偏移阶段自动吸收 | 标定/建图自动补偿 |
| `stage` | 需要跑离线标定阶段（ground / driven / camtime / axle） | 需运行离线标定阶段 |
| `procedure` | 需要改采集或回放流程（重录、拆分、限速、清盘） | 需调整采集或回放流程 |
| `none` | 标定与流程都救不回精度（参考系统 / 硬件 / 场景本身） | 标定无法补救 |

**警示 = 状态 ∈ {关注, 异常} 且 类别 ∈ {procedure, none}**。部分指标关注级可自动补偿、异常级不可（`fix_bad`），表中以「关注→auto / 异常→none」表示。

### 3.1 完整性与覆盖（缺失或断裂的数据没有任何算法能补回）

| 指标 | 阈值 | 类别 | 依据 |
|---|---|---|---|
| 必需话题 | 0 项缺失 | none | 4 路 LiDAR、`imu_data`、`imu_data/odometry`、`imu_data/ins_status`、相机（可选） |
| LiDAR 路数 | ≥4 正常 · ≥1 关注 | none | 合帧器按 4 路设计（源标签 0–3） |
| 分段覆盖断裂（>0.5 s） | 0 处 | none | 断裂处 IMU 积分中断，等同重新起步 |
| 重复 / 乱序消息 | ≤0.5 % 正常 · ≤2 % 关注 | auto | truck05 分段边界 621 条重复（0.23 %）——回放器按时间戳合并时丢弃，无影响；大量乱序会破坏合帧 |
| 相机话题 | 有 / 无 | — | 无相机 → 仅 LIO 可用 |

### 3.2 时间同步

| 指标 | 阈值 | 类别 | 依据 |
|---|---|---|---|
| IMU 采样间隔 | ≤11 ms 正常 · ≤21 ms 关注 | none | 100 Hz 设计；滤波器传播步长 |
| IMU 最大断点 | ≤15 ms 正常 · ≤100 ms 关注 | 关注→auto / 异常→none | truck05 3 次 60 ms 断点（首个 77.2 s）：yaml 断点上限内，前端跨帧传播即可；>100 ms 预积分误差不可恢复 |
| IMU 断点数（>20 ms） | 0 正常 · ≤5 关注 | 同上 | 同上 |
| LiDAR 丢帧率（最差一路） | ≤0.1 % 正常 · ≤1 % 关注 | none | 录制本身的丢帧（≠ 回放传输丢帧，后者见 §3.7 读取带宽） |
| 多雷达扫描起始离散 P99 | ≤1 ms 正常 · ≤5 ms 关注；单独统计 >1 ms / >5 ms 帧数 | 关注→auto / 异常→none | truck29 0.71 ms、truck05 1.14 ms（287 帧 >1 ms）；合帧容差 5 ms（guard 用 tol 5 ms 通过），>5 ms 的帧被合帧器丢弃 |
| 录制时间 − 传感器时间戳 | ≤300 ms 正常 · ≤1 s 关注 | none | 大偏移说明设备时钟未同步，时间偏移标定的 ±0.2 s 搜索窗兜不住 |

### 3.3 参考系统 RTK / INS（融合与评估都无法区分的参考噪声——精度下限）

| 指标 | 阈值 | 类别 | 依据 |
|---|---|---|---|
| RTK 固定解占比 | ≥99 % 正常 · ≥95 % 关注 | none | 浮点解位置误差分米级，融合权重按固定解设计 |
| 可用卫星数 P10 | ≥30 正常 · ≥20 关注 | none | truck29 P10 37 颗、truck05 23 颗；卫星数直接决定固定解几何强度与逐历元抖动 |
| INS 里程计断点（>50 ms） | 0 正常 · ≤3 关注 | 关注→auto / 异常→none | 后端按时间戳插值，个别断点可跨越 |
| 参考位置阶跃事件（>4 cm / 0.1 s，5 样本平滑，聚类计数） | ≤5 次/10 min 正常 · ≤150 关注；显示最大幅值与首次时刻 | none | §12.3：truck05 每 ~3 s 一次 3–11 cm 的位置回弹（72 次，最大 13.7 cm），在 evaluation 里表现为"误差"；truck29 的保持+双步伪影净位移为零，已由平滑与聚类剔除（0 次） |
| 参考位置停顿样本 | ≤3 % 正常 · ≤10 % 关注 | none | truck29 1.7 %（INS 输出保持一拍再补两步）；停顿本身不产生误差，但比例高说明 INS 输出链路不稳 |
| 参考位置-速度一致性 xy P95（0.5 s 窗） | ≤3 cm 正常 · ≤8 cm 关注 | none | 0.5 s 内位置增量与 INS 速度积分之差：truck29 2.16 cm、truck05 4.91 cm；这是 RTK 位置的逐历元抖动，也是"不要追求贴近 RTK"的量化依据 |
| 参考高程-速度一致性 z P95 | ≤3 cm 正常 · ≤12 cm 关注 | none | truck29 1.37 cm、truck05 10.27 cm；高程噪声通常是平面的 2–3 倍，决定坡道上的 z 精度 |
| INS 航向 vs 轨迹方向（中位） | ≤1° 正常 · ≤2.5° 关注 | stage | 常数偏差可由后轴/航向阶段标掉；显示 P95 抖动供参考 |
| 俯仰积分高程 vs RTK 高程 P95（每 100 m，去常数偏差） | ≤25 cm/100 m 正常 · ≤45 关注 | none | §12.3：truck05 z 误差随坡度出现（39.4 cm/100 m，最大 51.4；truck29 19.3）：INS 姿态与 RTK 高程在坡上互相矛盾，杠杆臂假设已排除 |
| INS 协方差字段 | 信息项 | — | 两车全 0 → 后端按固定权重融合（说明为何不能用 INS 协方差自适应加权） |
| INS 姿态四元数 | 0 条异常 · ≤10 关注 | none | 非单位 / NaN 四元数 |

| 指标 | 阈值 | 类别 | 依据 |

| 静止段雷达间地面倾角差（最大） | ≤0.2° 正常（低于自检生效阈值）· ≤1.0° 关注（自检自动修正）· ≤3° 需 ground/driven 阶段 · 更大 = 安装/文件错误 | auto / stage / none | 起步自检门限：旋转 ≤1.0°、高度 ≤0.15 m 自动应用，最小应用量 0.2° / 4 cm；truck05 front_left 0.28°（左右向）与建图自检 0.22° 一致 |

## 4. 判定与页面

- 组状态 = 组内最差指标；总结论 = 所有组最差；`outlook` 文案三档：全部正常 →「数据质量达到 truck29 参照水平（预期 xy 最大误差 ≤ 8.5 cm）」；有关注级警示 →「N 项关注级问题无法通过标定补救……误差预期高于 truck29」；有异常级警示 →「存在不可补救的异常，需重新采集」。
- 页面结构（保持控制台既有风格：卡片、`.callout`、`.badge`、`<details>`）：标题 + 结论徽标 + 生成时间 / 用时 / 所用标定 + 按钮 → 结论横幅（正常/关注/异常/不可补救 四个计数）→ **⚠ 警示区**（每条：组 · 指标 · 数值 · 一句话原因 · 「标定无法补救」标签）→ 可补偿区（蓝色，说明跑哪一步流水线）→ 7 个分组卡片（每行：状态点 / 指标 / 等宽数值 / 阈值 + 补救标签；卡片底部「说明与依据」折叠）→ 相机样例缩略图条（时刻 · 亮度均值 · 过曝 % · 纹理）→ 评估范围 / 消息数 / 报告路径。
- 分段明细表改为折叠（>10 段默认收起），避免 truck05 的 48 段把评估卡片顶到页面底部；≤10 段保持展开。
- 页面在无头浏览器中以三种状态（未评估 / truck29 正常 / truck05 关注）实际渲染检查，无 JS 错误。

## 5. 两车实测（Studio 作业 `assess`，2026-09-29）

| 指标 | truck29（120 s，3.7 GB） | truck05（720 s，24.7 GB） |
|---|---|---|
| 结论 / 用时 | **正常**（40 ok · 2 信息）/ 7.0 s | **关注**（30 ok · 10 关注 · 0 异常，5 项警示）/ 36 s |
| 重复消息 | 0 | 621（0.23 %，分段边界）→ 正常 |
| IMU 最大断点 / 断点数 | 10 ms / 0 | 60 ms / 3（首个 77.2 s）→ 关注，自动补偿 |
| 多雷达起始离散 P99 | 0.71 ms（0 帧 >1 ms） | 1.14 ms（287 帧 >1 ms，0 帧 >5 ms）→ 关注，合帧容差吸收 |
| RTK 固定解 / 卫星 P10 | 100 % / 37 | 100 % / **23 → 警示** |
| 参考位置阶跃事件 | 0 | **72 次（100/10 min，最大 13.7 cm，首个 60.2 s）→ 警示** |
| 参考位置停顿 | 1.71 % | 0.12 % |

| INS 航向 vs 轨迹 | −0.16°（P95 抖动 2.78°） | −0.06°（2.45°） |
| 静止段地面倾角差 / 高度差 | 0.16° / 0.9 cm（front_right） | 0.28°（front_left 左右向）/ 0.3 cm → 关注，自检自动修正（建图自检实测 0.22°） |
| 相机 | 30 fps，抖动 0，纹理最弱 430，过曝 0 % | 30 fps，抖动 0.02 ms，纹理最弱 2194，过曝 0 % |
| 路线 | 585 m，2 转弯，16 直线窗，≈231 关键帧，静止 4.5 s | 1542 m，9 转弯，46 直线窗，≈866 关键帧，静止 47.7 s |
| 资源 | 120 GB 可用，读取 661 MB/s（21×码率） | 120 GB，711 MB/s（21×） |

解读：

1. truck05 的 5 项警示全部属于参考系统，与 §12.3 的误差解剖完全对应——RTK 逐历元抖动（xy 4.9 cm）、周期性位置回弹（13.7 cm）、坡道上的高程矛盾（39 cm/100 m）直接构成 evaluation 中 8–10 cm 的"误差"，任何外参 / 时间偏移微调都不改变这些数值。评估把这一事实在数据准备阶段就摆到操作者面前，而不是在建图评估后再去解剖。
2. truck05 的可补偿项（IMU 断点、雷达起始离散、front_left 0.28° 倾角）已经被现有流程处理：yaml 断点容差、合帧 5 ms 容差、起步自检 0.2°–1.0° 自动应用；这与 v025_driven 实测（LIVO 8.04 cm、0–480 s LIO 8.25 cm）一致。
3. 动态障碍（车辆 / 人员）不在本评估范围：单次流式读取无法可靠区分动态点，且 §12 已证明 truck05 差异的主因不是动态物体。

## 6. 地面阶段决策：不新增"行驶段地面修后雷达残余俯仰"

- 现状：`scripts/refine_multi_lidar_extrinsics.py`（driven）第 2 遍对每路雷达在行驶段用地面 + 结构约束解 6-DoF，后雷达俯仰已在其中；v066 结果：后雷达地面厚度 4.00 → 3.12 cm，z −1.9 cm；guard 中后雷达沿轨中位 1.3 cm、墙面前后差 2.0 cm。
- 静止段地面阶段（`refine_multi_lidar_yaw.py` / ground）对后雷达无重叠地面（几何事实，见 §3.4），本就不是后雷达俯仰的来源。
- 新增一个只针对后雷达的行驶段地面阶段需要再读一遍数据（truck29 ≥ 1 min，truck05 ≥ 6 min），而可提高的量已被 driven 第 2 遍覆盖；在"不影响效率才做"的前提下，收益为零、成本为正 → 不做。评估报告中的静止段倾角项已覆盖"是否需要跑 ground/driven"的判断。
